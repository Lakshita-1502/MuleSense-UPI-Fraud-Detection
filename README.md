> This is a small classroom demo. All data is synthetic (generated by the code). It is not connected to any real
> bank or payment system, and its numbers must not be read as real-world accuracy.

## What it does
MuleSense shows how a machine learning model could flag a bank account that behaves like a mule account
(many new payers from many states, money leaving within the hour, sudden activity), the behaviour reported in the case.

1. **Score an account** - pick a sample account or set its behaviour with sliders; get a risk score, a suggested
   action (no action / watch / review / hold) and the reasons for the score.
2. **Case replay** - scores 60 simulated accounts (one for each account the report says was used), with payer states
   drawn from the state-wise complaint counts of the case.
3. **Model report** - precision, recall, F1, PR-AUC, confusion matrix, precision-recall curve, feature importance.
4. **Forensic audit log** - each logged decision is stored with a SHA-256 hash linked to the previous record;
   a verify button and a tamper test show that editing an old record is detected.

## How to run (step by step, starting from clone)

### Step 1 - Clone the repository
Open a terminal (Git Bash, Command Prompt, PowerShell or the VS Code terminal) in the folder where you want the project:
```
git clone https://github.com/Lakshita-1502/MuleSense-UPI-Fraud-Detection.git
cd MuleSense-UPI-Fraud-Detection
```
(If you downloaded the project as a zip instead, unzip it and `cd` into the folder that contains `app.py`.)

### Step 2 - Start the app

1. Create a virtual environment:
   ```
   python -m venv venv
   ```
2. Activate it (use the line that matches your terminal):
   ```
   venv\Scripts\activate              # Windows Command Prompt / PowerShell
   source venv/Scripts/activate       # Windows Git Bash
   source venv/bin/activate           # Linux / macOS
   ```
   The prompt should now start with `(venv)`.

3. Install the libraries:
   ```
   pip install -r requirements.txt
   ```
4. Start the dashboard:
   ```
   streamlit run app.py
   ```
   If `streamlit` is not recognised, use `python -m streamlit run app.py`.

### Step 3 - Open the dashboard
The browser opens automatically at **http://localhost:8501**. If it does not, type that address into your browser.
The model trains in about 2 seconds on first load. If Streamlit asks for an email on first start, press Enter to skip.

### Step 4 - Stop the app
Press **Ctrl+C** in the terminal (or close the launcher window). To run again later, repeat Step 2
(if you used Option B, activate the venv first).

## Quick demo script (about 5 minutes)
1. **Score an account:** pick "Typical genuine account" (no action), then "Obvious mule account" (hold).
   Show the bar chart "Why this score?" - the pass-through ratio dominates.
2. Pick "Busy shop" - busy but genuine, still no action. Pick "Stealthy mule" - goes to analyst review.
   Click **Log this decision to the audit trail**.
3. **Case replay:** about 50 of the 60 case-style accounts are flagged. Click **Log all flagged accounts**.
4. **Model report:** metrics, confusion matrix and the "accuracy trap" note (calling every account genuine is about
   98.6% accurate and catches no mule).
5. **Forensic audit log:** "Chain verified". Click **Simulate an attacker changing a score** - verification fails
   at the edited record. Use **Clear log** before the next demo.

## How it works (short)
- **Data:** 30,000 synthetic accounts, about 1.5% mule accounts; 40% of mules are "stealthy" (look almost normal)
  and some genuine accounts are busy like shops. Seed 42, so results repeat.
- **Model:** XGBoost (300 trees, depth 4). 70/30 split, then 80/20 train/validation. The alert threshold is chosen
  on validation data (best F1) and the test set is used once.
- **Explanations:** XGBoost's built-in per-feature contributions (TreeSHAP).
- **Audit log:** each JSON record includes the previous record's hash; `verify_log()` recomputes the chain.

## Limitations
Synthetic data built from our own assumptions, because the case report gives no behavioural numbers. The data split
is random, not time-based. The audit log is a local file with no login or external time-stamping. This is a
demonstration, not a production fraud system.

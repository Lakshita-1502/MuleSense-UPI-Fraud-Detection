## What it does
MuleSense shows how a machine learning model could flag a bank account that behaves like a mule account
(many new payers from many states, money leaving within the hour, sudden activity), the behaviour reported in the case.

1. **Score an account** - choose a sample account or set its behaviour with sliders; get a risk score,
   a suggested action (no action / watch / review / hold) and the reasons for the score.
2. **Case replay** - scores 60 simulated accounts (one for each account the report says was used), with payer states
   drawn from the state-wise complaint counts of the case.
3. **Model report** - precision, recall, F1, PR-AUC, confusion matrix, precision-recall curve, feature importance.
4. **Forensic audit log** - every logged decision is stored with a SHA-256 hash linked to the previous record;
   a verify button and a tamper test show that editing an old record is detected.

## Quick demo script (about 5 minutes)
1. **Score an account:** pick "Typical genuine account" (no action), then "Obvious mule account" (hold).
   Show the bar chart "Why this score?" - the pass-through ratio dominates.
2. Pick "Busy shop" - busy but genuine, still no action. Pick "Stealthy mule" - goes to analyst review.
   Click **Log this decision to the audit trail**.
3. **Case replay:** about 50 of the 60 case-style accounts are flagged. Click **Log all flagged accounts**.
4. **Model report:** metrics, confusion matrix, and the "accuracy trap" note (calling everything genuine is about 98.6% accurate and catches no mule).
5. **Forensic audit log:** "Chain verified". Click **Simulate an attacker changing a score** - verification fails at the edited record.
   Use **Clear log** before the next demo.

## How it works (short)
- **Data:** 30,000 synthetic accounts, about 1.5% mule accounts, 40% of mules "stealthy" (look almost normal),
  some genuine accounts busy like shops. Seed 42, so results repeat.
- **Model:** XGBoost (300 trees, depth 4). 70/30 split, then 80/20 train/validation. The alert threshold is chosen on
  validation data (best F1), and the test set is used once.
- **Explanations:** XGBoost's built-in per-feature contributions (TreeSHAP).
- **Audit log:** each JSON record includes the previous record's hash; `verify_log()` recomputes the chain.

## Limitations
Synthetic data built from our own assumptions; the case report gives no behavioural numbers. Random (not time-based)
split. The audit log is a local file with no login or external time-stamping. This is a demonstration, not a
production fraud system.
